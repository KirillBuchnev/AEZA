# AEZA — анализатор риска оттока

Панель для отдела удержания. Показывает, какие аккаунты и услуги могут не продлиться, почему, какое действие нужно и сколько денег под угрозой. Отдельно показывает отток: что уже произошло по журналу снимков и сколько непродлений ожидается в ближайшие дни.

Интерфейс собран на React и Vite (макет — Figma «AEZA — Пульс продлений»), API — FastAPI, данные и настройки хранятся в SQLite. В `db/` лежит проект схемы для PostgreSQL с описанием таблиц.

## Запуск

Нужен Docker с Compose.

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- Панель: <http://localhost:5173>
- API и Swagger: <http://localhost:8001/api/v1/docs>
- OpenAPI JSON: <http://localhost:8001/api/v1/openapi.json>
- Health check: <http://localhost:8001/healthz>

Локальный демо-вход по умолчанию:

```text
Логин: demo
Пароль: local-demo-change-this-password
Кодовое слово (для восстановления пароля): demo-codeword
```

Значения из примера подходят только для локального запуска. Перед публикацией задай собственные `AEZA_ADMIN_USERNAME`, `AEZA_ADMIN_PASSWORD`, `AEZA_ADMIN_CODEWORD`, `AEZA_RATE_LIMIT_SECRET`, `AEZA_METRICS_TOKEN`, HTTPS origins и `AEZA_COOKIE_SECURE=true`. В production сервис не запустится со стандартными или небезопасными параметрами, Swagger выключен по умолчанию.

SQLite хранится в Docker volume `aeza-data`: снимок, журнал переходов, веса и пороги сохраняются после перезапуска.

### Фронтенд без Docker

```bash
cd frontend
npm install
AEZA_API_TARGET=http://127.0.0.1:8000 npm run dev -- --host 127.0.0.1
```

Vite проксирует `/api` и `/metrics` на `AEZA_API_TARGET`. Открывать по `http://127.0.0.1:5173` — этот origin разрешён в `AEZA_ALLOWED_ORIGINS`.

### Тесты

```bash
cd backend
pip install -r requirements-dev.txt
pytest
```

79 тестов: контрольные случаи модели, агрегация аккаунта, деньги, прогноз, журнал снимков, сортировка, версия расчёта, миграция настроек, регистрация и сброс пароля, ограничения частоты, OIDC с подставным провайдером.

## Архитектура

```text
браузер ──► nginx (frontend, 10.233.40.10) ──► FastAPI (api) ──► SQLite (volume aeza-data)
               │  статика React                  │  расчёт риска на лету
               │  /api, /metrics → api           │  SSE /api/v1/events
               └  limit_req на вход и сброс      └  /metrics для Prometheus
```

- `backend/app/risk.py` — модель: признаки, индекс услуги, агрегация аккаунта, причины, рекомендуемые действия, прогноз оттока. Чистые функции без доступа к базе.
- `backend/app/database.py` — снимок, журнал переходов между снимками, настройки модели, пользователи, сессии, ограничения частоты.
- `backend/app/main.py` — HTTP-контракт, сессии, сортировка и фильтры, SSE, метрики.
- `backend/app/oidc.py` — вход через OpenID Connect.
- `frontend/src` — экраны: вход, обзор, клиенты, карточка клиента, модель риска, источник данных.

Поток данных: источник присылает снимок `PUT /api/v1/source/snapshot` → API сравнивает его с предыдущим и пишет факты в журнал → сохраняет снимок и рассылает SSE-событие → панель перечитывает данные без перезагрузки. Оценки считаются при каждом запросе по текущему снимку, весам и времени, поэтому срочность растёт сама по мере приближения даты.

## Модель риска

Модель экспертная: веса заданы командой и согласованы с ментором кейса, а не обучены на исходах. Индекс показывает риск неоплаты продления, а не вероятность ухода клиента.

### Почему без машинного обучения

Для обучения нужны размеченные исходы: какие услуги в итоге продлились, а какие нет. В снимке кейса их нет, есть только текущее состояние. Обученная модель без исходов подгонялась бы под предположения, а не под реальность, и не могла бы объяснить, почему клиент в списке. Экспертный индекс прозрачен, его можно проверить вручную и настроить в панели.

Путь к ML заложен: журнал снимков накапливает переходы `prolong_wait → active` (продлено) и `→ deleted` (не продлено). Когда исходов станет достаточно, их можно использовать как метки: сначала откалибровать веса текущей формулы, затем сравнить с градиентным бустингом на тех же признаках по качеству и по стабильности объяснений.

### Признаки и веса

| Признак | Вес | Когда срабатывает |
| --- | ---: | --- |
| Ручное продление `autoprolong_disabled` | 45 | автопродление выключено, срок продления в ближайшие 7 дней |
| Нехватка средств `insufficient_balance` | 40 | доступного баланса не хватает на продление этой услуги |
| Срочность `renewal_urgency` | 20 | есть ручное продление или нехватка средств, вклад растёт к сроку |
| Ожидание оплаты `prolong_wait` | 5 | услуга уже ждёт оплаты, вклад растёт за 5 дней grace-периода |

Выключенное автопродление и нехватка денег — главные признаки: в первом случае клиенту нужно продлить услугу самому, во втором списание не пройдёт. Близкий срок усиливает риск, потому что на решение остаётся меньше времени. Статус `prolong_wait` весит мало: сам по себе он не означает потерю услуги. Если автопродление включено и денег хватает, списание пройдёт, и риск низкий.

### Формула

```text
urgency          = clip(1 − (due_at − now) / 7 дней, 0, 1)      # для prolong_wait = 1
manual_renewal   = urgency, если автопродление выключено
payment_distress = clip(недостаток_по_услуге / цена, 0, 1) × urgency
renewal_urgency  = urgency, если есть manual_renewal или payment_distress
grace_progress   = прошло_дней_ожидания / 5, только для prolong_wait

индекс услуги   = 100 × (45·manual_renewal + 40·payment_distress + 20·renewal_urgency + 5·grace_progress) / Σвесов
индекс аккаунта = Σ индексов услуг
```

Нормализатор — сумма весов (по умолчанию 110), поэтому индекс услуги всегда от 0 до 100 при любых весах из панели. Индекс считается с одним знаком после запятой.

Баланс аккаунта общий: доступный баланс (основной плюс бонусный, если `bonusState = unlocked`; выводимый не считается) распределяется по услугам в порядке оплаты — сначала ожидающие оплаты, затем по ближайшей дате продления.

### Контрольные случаи

Четыре аккаунта из обсуждения с ментором, у каждого одна услуга за 10 €:

| Ситуация | Индекс | Уровень | Ментор |
| --- | ---: | --- | --- |
| а. `prolong_wait` 1 день, баланс 0 | 55.5 | высокий | высокий |
| б. продление через 3 часа, автопродление выключено, денег хватает | 58.0 | высокий | высокий |
| в. продление через 3 часа, автопродление включено, баланс 0 | 53.6 | высокий | высокий |
| г. `prolong_wait` 1 день, автопродление включено, денег хватает | 0.9 | низкий | низкий |

Эти значения закреплены тестами `backend/tests/test_model_contract.py`. На странице модели они пересчитываются из текущих весов, поэтому видно, как изменение коэффициента сдвигает контрольные случаи.

### Уровни

Уровень услуги: средний от 30, высокий от 50. Уровень аккаунта считается по сумме индексов его услуг и имеет свои пороги (по умолчанию тоже 30 и 50). Их можно поднять отдельно, чтобы аккаунт с сотнями услуг с небольшим риском не всегда попадал в высокий.

Если у активной услуги нет даты окончания или дата уже прошла, у услуги нет индекса, у аккаунта — тоже: такой аккаунт получает «Нет оценки» и задачу на исправление данных. Остальные услуги этого аккаунта всё равно рассчитываются и видны в карточке.

### Почему клиент в списке

Каждая причина приходит с вкладом в баллах и аргументом с цифрами из данных, например:

- «На продление хватает 0,00 € из 100,00 €, не хватает 100,00 €. Без пополнения списание не пройдёт.»
- «Автопродление выключено, продление через 3 ч. Клиент должен продлить услугу сам, иначе она уйдёт в ожидание оплаты.»
- «Услуга ожидает оплаты 1,0 дн. после окончания срока; осталось 4 дн. grace-периода.»

Сумма вкладов равна индексу услуги с точностью до округления. Для каждой услуги и аккаунта есть рекомендуемое действие: пополнить баланс на конкретную сумму, напомнить о ручном продлении, проверить списание или исправить данные. Неуспешная оплата за последние 7 дней в индекс не входит (по одному снимку нельзя отличить сбой от отказа), но попадает в рекомендацию.

### Деньги

```text
продления под риском   = Σ цена услуги × индекс / 100
потенциальная потеря   = Σ недостаток на продление услуги × индекс / 100
стоимость в месяц      = Σ цена услуги / месяцев в сроке оплаты (month, quarter, half_year, year)
```

Значения — ориентир для очереди, а не финансовый прогноз. Для сортировки по ценности клиента есть стоимость в месяц (регулярный доход) и сумма пополнений за всё время (лояльность): ментор предложил оставить выбор маркетологу.

### Отток: факты и прогноз

- **Факты** берутся из журнала снимков. При каждой загрузке API сравнивает новый снимок с предыдущим и записывает переходы: продлено, ушло в ожидание оплаты, удалено, заблокировано, пропало из источника. Первый загруженный снимок журнал только открывает; демо-данные в журнал не попадают.
- **Прогноз** — ожидаемое число непродлений по дням окончания: сумма индексов услуг с этой датой, делённая на 100. Это оценка по индексу, она не откалибрована по историческим исходам.

На обзоре факты и прогноз показаны на одной оси времени и визуально разделены: факты сплошные слева от линии «сегодня», прогноз штрихованный справа.

### Как добавить признак

1. В `backend/app/risk.py` добавить вес в `DEFAULT_WEIGHTS`, описание в `FACTORS`, вклад в словарь `contributions` внутри `_evaluate_service` и текст аргумента в `_explain`.
2. Допустимые ключи весов в `PATCH /api/v1/model/settings` берутся из `DEFAULT_WEIGHTS`, нормализатор пересчитывается сам.
3. Панель получает список признаков из `GET /api/v1/model/settings`, поэтому новый признак появляется на странице модели без правки фронтенда.
4. Добавить контрольный случай в `backend/tests/test_model_contract.py`.

Каждое изменение весов увеличивает ревизию настроек. Ответы API содержат `calculation_version` (версия модели и ревизия) и `snapshot_id`, поэтому видно, по каким данным и каким весам получена оценка. При обновлении базы старого формата настройки мигрируют с сохранением весов и порогов.

## Пользователи и вход

- **Регистрация** — фамилия, имя, отчество (необязательно), логин, пароль и кодовое слово. Включена в разработке и выключена в production по умолчанию; управляется `AEZA_REGISTRATION_ENABLED`.
- **Забыли пароль** — логин и кодовое слово (регистр не важен), затем новый пароль. Токен сброса живёт 10 минут и срабатывает один раз. После сброса все сессии пользователя закрываются.
- **Смена пароля** — из боковой панели, с проверкой текущего пароля. Остальные сессии завершаются.
- **Правила** — пароль от 10 до 128 символов, буквы и цифры, не совпадает с логином. Кодовое слово от 6 до 64 символов, не только цифры и не типовое слово. Логин от 3 до 64 символов: латиница, цифры, `. _ @ -`. Пароль и кодовое слово хранятся как scrypt-хеши.
- **Защита от перебора** — за 15 минут: 5 неверных входов с одного адреса и 10 на один логин; 30 проверок кодового слова с адреса и 5 на логин; 5 попыток смены пароля. Адрес клиента берётся из `X-Real-IP` только от прокси из `AEZA_TRUSTED_PROXY_IPS`. Локально Docker подменяет адрес на шлюз сети, поэтому все браузеры одной машины делят лимиты.
- **Первый администратор** создаётся из `AEZA_ADMIN_*`, только если такого логина ещё нет.

### Вход через SSO (OpenID Connect)

Включается переменными:

```text
AEZA_OIDC_ISSUER=https://sso.example.com/realms/aeza
AEZA_OIDC_CLIENT_ID=aeza-panel
AEZA_OIDC_CLIENT_SECRET=...            # для конфиденциального клиента
AEZA_OIDC_REDIRECT_URI=https://panel.example.com/api/v1/auth/oidc/callback
AEZA_OIDC_SCOPES=openid profile email
AEZA_OIDC_AUTO_PROVISION=false         # true — создавать пользователя при первом входе
AEZA_OIDC_USERNAME_CLAIM=preferred_username
```

Поток — authorization code с PKCE (S256), `state` и `nonce` одноразовые и живут 10 минут. `id_token` проверяется по ключам JWKS провайдера: подпись (только асимметричные алгоритмы), `iss`, `aud`, `exp`, `nonce`. Учётная запись SSO связывается с локальной по паре issuer и subject. Автоматически связать SSO с уже существующим локальным логином нельзя, чтобы чужая учётная запись провайдера не получила доступ к чужому аккаунту. У SSO-пользователя нет локального пароля. Вход по паролю остаётся запасным вариантом: кнопка SSO появляется на экране входа, только когда провайдер настроен (`GET /api/v1/auth/methods`).

## API

Все endpoints под `/api/v1`, кроме `/metrics` и `/healthz`. Данные клиентов, настройки и импорт требуют HTTP-only cookie-сессию. Для Prometheus — отдельный `AEZA_METRICS_TOKEN` в заголовке `Authorization: Bearer`.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/auth/methods` | Доступные способы входа |
| `POST` | `/auth/login` | Вход по логину и паролю |
| `GET` | `/auth/oidc/login`, `/auth/oidc/callback` | Вход через SSO |
| `GET` | `/auth/me` | Текущий пользователь |
| `POST` | `/auth/logout` | Выход |
| `POST` | `/auth/register` | Регистрация |
| `POST` | `/auth/password/verify-codeword` | Проверка кодового слова, выдаёт токен сброса |
| `POST` | `/auth/password/reset` | Новый пароль по токену сброса |
| `POST` | `/auth/password/change` | Смена пароля в сессии |
| `GET` | `/customers` | Очередь клиентов: поиск, фильтры, сортировка, страницы |
| `GET` | `/customers/{id}` | Услуги, причины с аргументами, действия, качество данных, расчёт |
| `GET` | `/analytics/summary` | Уровни, деньги, причины, топ потерь |
| `GET` | `/analytics/outflow?days=30` | Факты журнала и прогноз непродлений |
| `GET` | `/model/settings` | Веса, пороги, признаки, версия расчёта |
| `PATCH` | `/model/settings` | Изменение весов и порогов с пересчётом |
| `PUT` | `/source/snapshot` | Загрузка снимка, отчёт о качестве данных |
| `GET` | `/events` | SSE-обновления панели |
| `GET` | `/metrics` | Метрики Prometheus |

Сортировка клиентов: `sort_by=risk_score|potential_loss|revenue_at_risk|monthly_cost|total_replenished|due_revenue|balance|high_count|max_service_score|service_count|email|id`, `order=asc|desc`. Клиенты без оценки всегда в конце. Фильтры: `risk_level=high|medium|low|unscored`, `reason=autoprolong_disabled|insufficient_balance|renewal_urgency|prolong_wait`, `data_status=all|clean|issues`, поиск `q` по ID и email.

### Загрузка данных

```bash
curl -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"username":"demo","password":"local-demo-change-this-password"}' \
  http://localhost:8001/api/v1/auth/login

curl -b cookies.txt -X PUT -H 'Content-Type: application/json' \
  --data @snapshot.json http://localhost:8001/api/v1/source/snapshot
```

Формат `snapshot.json` — `{"customers": [...]}`, поля кейса в `camelCase` (`balance`, `withdrawBalance`, `bonusBalance`, `bonusState`, `totalReplenished`, `services[].price`, `autoprolong`, `paymentTerm`, `status`, `expiresAt`, `transactions[]`) или нормализованные `*_minor`. Деньги — в евроцентах. Ответ содержит `snapshot_id`, число записанных фактов журнала, отчёт о качестве данных и сводку. Тот же файл можно загрузить на странице «Источник данных».

Лимиты: до 5 000 клиентов, до 5 000 услуг и 10 000 транзакций на клиента, не больше 50 000 услуг и транзакций в снимке.

## Безопасность и эксплуатация

Сессии хранят только SHA-256 хеши случайных токенов. Cookie `HttpOnly`, `SameSite=Lax`, в production обязателен `Secure`. Изменяющие запросы проверяют `Origin` и Fetch Metadata. API разрешает браузерные запросы только с origins из `AEZA_ALLOWED_ORIGINS`. SSE-очереди ограничены и отбрасывают старые события.

Compose запускает API от непривилегированного пользователя с read-only root filesystem, без Linux capabilities и с `no-new-privileges`. Интерфейс отдаётся с CSP и защитными заголовками, шрифты хранятся локально.

Метрики Prometheus: `aeza_customers_total{risk_level}`, `aeza_potential_loss_eur`, `aeza_revenue_at_risk_eur`, `aeza_monthly_cost_eur`, `aeza_services_at_risk`, `aeza_expected_non_renewals`, `aeza_customers_assessed_total`.
