# AEZA — анализатор риска оттока

Панель аналитика оценивает риск непродления услуг, объясняет активные признаки и показывает ориентировочную сумму выручки под угрозой. Интерфейс собран на React и Vite, API — FastAPI, данные и настройки хранятся в SQLite.

## Запуск

Нужен Docker с Compose.

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- Панель аналитика: <http://localhost:5173>
- API и Swagger: <http://localhost:8001/api/v1/docs>
- OpenAPI JSON: <http://localhost:8001/api/v1/openapi.json>
- Health check: <http://localhost:8001/healthz>

Локальный демо-вход по умолчанию:

```text
Логин: demo
Пароль: local-demo-change-this-password
Кодовое слово (для восстановления пароля): demo-codeword
```

Значения из примера предназначены только для локального запуска. Перед публикацией задай собственные `AEZA_ADMIN_USERNAME`, `AEZA_ADMIN_PASSWORD`, `AEZA_RATE_LIMIT_SECRET`, HTTPS origins и `AEZA_COOKIE_SECURE=true`. В production сервис остановится при небезопасных или стандартных параметрах; Swagger/OpenAPI выключены по умолчанию. Интерфейс работает на порту 5173, API доступен локально на порту 8001 (значение задаётся `AEZA_API_PORT`). Запросы интерфейса проходят через обратный прокси, так что браузерная сессия остаётся на одном origin.

SQLite хранится в Docker volume `aeza-data`: снимок данных, веса и пороги модели сохраняются после перезапуска контейнера.

### Фронтенд без Docker

```bash
cd frontend
npm install
AEZA_API_TARGET=http://127.0.0.1:8000 npm run dev -- --host 127.0.0.1
```

Vite проксирует `/api` и `/metrics` на `AEZA_API_TARGET` (по умолчанию `http://127.0.0.1:8000`). Открывать по `http://127.0.0.1:5173` — этот origin разрешён в `AEZA_ALLOWED_ORIGINS`.

Экраны: вход, обзор (кому нужно внимание, почему, сколько можем потерять), клиенты с сортировкой по ID, email, балансу, пополнениям и риску в обе стороны, карточка клиента с вкладом каждого признака и расчётом потерь, модель риска, источник данных (загрузка снимка, журнал обновлений, `/metrics`). Есть светлая и тёмная тема. Признаки на странице модели берутся из `GET /api/v1/model/settings`, поэтому новый признак бэкенда появляется в панели без правки фронтенда. Макет — в Figma «AEZA — Пульс продлений».

## Пользователи

Служебный вход из `.env` (`AEZA_ADMIN_USERNAME` / `AEZA_ADMIN_PASSWORD`) работает как раньше. Кроме него сотрудники регистрируются сами: фамилия, имя, отчество (необязательно), логин, пароль (от 8 символов) и кодовое слово. Кодовое слово нужно для сброса пароля: на экране входа «Забыли пароль?» просит логин, кодовое слово и новый пароль.

Пароли и кодовые слова хранятся только как хеши `scrypt` (стандартная библиотека Python). Кодовое слово сверяется без учёта регистра и лишних пробелов. Регистрация и сброс ограничены по частоте так же, как вход; на неверный логин и неверное кодовое слово ответ одинаковый, чтобы нельзя было перебрать логины. После сброса пароля все сессии пользователя закрываются.

## Модель риска

Это объяснимый экспертный индекс, а не обученный ML-прогноз и не вероятность ухода. Он считает риск каждой услуги, затем агрегирует его на аккаунт. Исходный кейс не содержит истории переходов статусов и удалений.

Для услуги в ближайшем периоде используется срочность:

```text
urgency = clip(1 − (due_at − now) / 7 дней, 0, 1)
```

Дефицит баланса распределяется между услугами по ближайшей дате продления. Индекс услуги использует нормализованную сумму компонентов:

```text
service_score = round(100 × clip(
  (40 × payment_distress
   + 45 × manual_renewal
   + 20 × renewal_urgency
   + 5 × grace_period_progress
   + 20 × recent_failed_payment × urgency) / 110,
  0, 1))
```

`payment_distress` — доля дефицита по услуге, `manual_renewal` — срочность при выключенном автопродлении, `grace_period_progress` применяется только к `prolong_wait`. Неуспешный платёж учитывается только за последние 7 дней и по соответствующей услуге.

В ответе API `reasons[].points` — это фактический динамический вклад причины. Он меняется с текущим временем до продления, размером дефицита и прогрессом grace-периода; это не фиксированная прибавка за попадание в этап. Компонент общей срочности распределяется между активными причинами, поэтому сумма отображаемых `+баллов` соответствует расчёту индекса услуги.

Начальные веса и пороги:

| Признак | Начальный вес |
| --- | ---: |
| Grace-прогресс для `prolong_wait` | 5 |
| Скорое продление при выключенном автопродлении | 45 |
| Недостаточно доступного баланса на продление | 40 |
| Недавняя неуспешная транзакция продления | 20 |

Высокий риск начинается с 50, средний — с 30. Поэтому ручное продление через несколько часов и нехватка средств перед автопродлением попадают в высокий риск, а `prolong_wait` при достаточном балансе остаётся низким до завершения grace-периода.

Для аккаунта API дополнительно возвращает `account_risk_sum`, `max_service_score`, `high_count`, `revenue_at_risk_minor` и `uncovered_revenue_at_risk_minor`. Эти значения — индексы и ориентиры для очереди, а не финансовая гарантия.

Денежная оценка считается так:

```text
недопокрытая сумма = max(стоимость продлений за период − доступный баланс, 0)
потенциальная потеря = сумма(дефицит услуги × score услуги / 100)
```

Доступный баланс — основной баланс плюс бонусный, если `bonusState` разрешает его тратить. Выводимый баланс не считается средствами для автопродления. Все поля `balance`, `price`, `amount` и `totalReplenished` принимаются в минимальных денежных единицах (евроценты); API хранит и возвращает их как поля `*_minor`.

Если у клиента нет активных/ожидающих продления услуг, отсутствует дата окончания или активная услуга уже истекла, он получает статус «Нет оценки» и причину data quality. Для `prolong_wait` API возвращает `grace_remaining_days`.

Порог, горизонт прогноза и веса редактируются через API. PATCH настроек сохраняет изменения в SQLite и рассылает SSE-событие активным клиентам. При обновлении старого SQLite-файла настройки мигрируют на версию этого алгоритма.

## Аутентификация

- **Регистрация** — логин, имя, фамилия, пароль и кодовое слово. Почты нет: кодовое слово нужно только для восстановления пароля. Регистрация включена по умолчанию в разработке и выключена в production; управляется `AEZA_REGISTRATION_ENABLED`.
- **Забыли пароль** — вход по логину и кодовому слову (регистр не важен). Затем задаётся новый пароль. Токен сброса действует 10 минут и работает один раз.
- **Смена пароля** — из боковой панели, с проверкой текущего пароля. После смены остальные сессии завершаются.
- **Правила пароля** — от 10 до 128 символов, буквы и цифры, не совпадает с логином. Пароль и кодовое слово хранятся в виде scrypt-хеша, открытых значений в базе нет.
- **Кодовое слово** — от 6 до 64 символов, не только цифры и не типовое слово (`password`, `qwerty` и т. п.), не совпадает с паролем.
- **Защита от перебора** — за 15 минут: 5 неверных входов с одного адреса и 10 на один логин с любых адресов; 30 проверок кодового слова с одного адреса и 5 на один логин; 5 неверных попыток смены пароля. Адрес клиента берётся из `X-Real-IP` только от прокси из `AEZA_TRUSTED_PROXY_IPS`: в compose это фиксированный адрес контейнера frontend (`10.233.40.10`, сеть `10.233.40.0/24`). Для nginx те же ограничения частоты действуют на регистрацию и все маршруты `/api/v1/auth/password/*`. Ограничение локального запуска: Docker подменяет адрес клиента на шлюз сети, поэтому все браузеры одной машины делят одни лимиты. При развёртывании за своим прокси лимиты считаются по реальному адресу клиента.
- **Первый администратор** создаётся из `AEZA_ADMIN_USERNAME`, `AEZA_ADMIN_PASSWORD` и `AEZA_ADMIN_CODEWORD`, только если такого логина ещё нет. Потом пароль меняется в панели, а не через переменные окружения.

Тесты авторизации: `cd backend && pip install -r requirements-dev.txt && pytest`.

## API

Все endpoints под `/api/v1`, кроме `/metrics` и `/healthz`. Данные клиентов, настройки и импорт снимка требуют действующую HTTP-only cookie-сессию. Для Prometheus используется отдельный `AEZA_METRICS_TOKEN` и Bearer token. Локальный compose задаёт демонстрационный токен из `.env.example`; перед публикацией его нужно заменить. Пример scrape-конфигурации:

```yaml
scrape_configs:
  - job_name: aeza
    metrics_path: /metrics
    static_configs:
      - targets: ["api:8000"]
    authorization:
      type: Bearer
      credentials: ${AEZA_METRICS_TOKEN}
```

Swagger и OpenAPI доступны в development; в production они выключены по умолчанию (`AEZA_DOCS_ENABLED=true` включает их явно).

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/auth/login` | Создать сессию по логину и паролю |
| `GET` | `/api/v1/auth/me` | Текущий пользователь |
| `POST` | `/api/v1/auth/logout` | Завершить сессию |
| `POST` | `/api/v1/auth/register` | Регистрация: ФИО, логин, пароль, кодовое слово |
| `POST` | `/api/v1/auth/password-reset` | Сброс пароля по логину и кодовому слову |
| `GET` | `/api/v1/customers` | Рейтинг, поиск, фильтр и сортировка |
| `GET` | `/api/v1/customers/{id}` | Услуги, транзакции, признаки и расчёт клиента |
| `GET` | `/api/v1/analytics/summary` | Сводные риски и потенциальная потеря |
| `GET` | `/api/v1/model/settings` | Действующие веса, пороги и описание признаков |
| `PATCH` | `/api/v1/model/settings` | Изменить часть настроек с автопересчётом |
| `PUT` | `/api/v1/source/snapshot` | Полностью заменить исходный снимок |
| `GET` | `/api/v1/events` | SSE для обновления панели без reload |
| `GET` | `/metrics` | Метрики Prometheus |
| `GET` | `/api/v1/docs` | Swagger UI |

Полная спецификация находится в [`backend/openapi.yaml`](backend/openapi.yaml). Входной формат снимка принимает поля кейса в `camelCase` (`balance`, `withdrawBalance`, `bonusBalance`, `bonusState`, `totalReplenished`, `autoprolong`, `paymentTerm`, `expiresAt`) и нормализованные поля `*_minor`.

Сортировка клиентов: `sort_by=id|email|balance|total_replenished|risk_score|potential_loss`, `order=asc|desc`. Пример: `/api/v1/customers?sort_by=balance&order=asc`.

## Данные и ограничения

При первом запуске создаётся небольшой синтетический снимок с адресами домена `.example`; он нужен только для демонстрации. Если в базе остаётся именно demo-источник, его даты обновляются при старте, поэтому демонстрация не протухает. Загруженный через API снимок никогда не перезаписывается демо-данными. Внешний набор тестовых данных сам не загружается. Передай снимок через `PUT /api/v1/source/snapshot`, когда он будет доступен в разрешённом формате. Снимок допускает до 5 000 клиентов, 5 000 услуг и 10 000 транзакций на клиента при общем лимите 50 000 записей каждого типа.

Сессии хранят только SHA-256 хеши случайных токенов. Cookie имеет флаги `HttpOnly` и `SameSite=Lax`; в production обязателен `Secure`. Вход ограничен по частоте в Nginx и по адресу сокета в SQLite; `X-Real-IP` учитывается только для IP, явно перечисленных в `AEZA_TRUSTED_PROXY_IPS` (в локальном Compose это фиксированный адрес reverse proxy `10.233.40.10`). Изменяющие запросы проверяют `Origin` и Fetch Metadata, неизвестные поля снимка игнорируются, а списки ограничены общим лимитом в API. SSE очереди ограничены и отбрасывают старые события, поскольку интерфейсу достаточно последнего состояния. API разрешает браузерные запросы только с origins, перечисленных в `AEZA_ALLOWED_ORIGINS`.

Docker Compose запускает API от непривилегированного пользователя с read-only root filesystem, без Linux capabilities и с `no-new-privileges`. Интерфейс отдаётся с CSP и защитными HTTP-заголовками; шрифты Exo 2 и Inter хранятся локально, внешние запросы к Google Fonts не нужны.
