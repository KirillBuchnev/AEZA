# AEZA — анализатор риска оттока

Панель аналитика оценивает экспертный индекс риска непродления услуг, объясняет факторы и показывает сценарную оценку стоимости продлений. Интерфейс собран на React и Vite, API — FastAPI, данные и настройки хранятся в SQLite.

## Запуск

Нужен Docker с Compose.

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- Панель аналитика: <http://localhost:5173>
- API и Swagger: <http://localhost:8001/api/v1/docs>
- OpenAPI JSON: <http://localhost:8001/api/v1/openapi.json>
- Health check: <http://localhost:8001/healthz>

Локальный демо-вход по умолчанию:

```text
Логин: demo
Пароль: local-demo-change-this-password
```

Значения из примера предназначены только для локального запуска. Перед публикацией задай собственные `AEZA_ADMIN_USERNAME`, `AEZA_ADMIN_PASSWORD`, `AEZA_RATE_LIMIT_SECRET`, HTTPS origins и `AEZA_COOKIE_SECURE=true`. В production сервис остановится при небезопасных или стандартных параметрах; Swagger/OpenAPI выключены по умолчанию. Интерфейс работает на порту 5173, API доступен локально на порту 8001 (значение задаётся `AEZA_API_PORT`). Запросы интерфейса проходят через обратный прокси, так что браузерная сессия остаётся на одном origin.

SQLite хранится в Docker volume `aeza-data`: снимок данных, веса и пороги модели сохраняются после перезапуска контейнера.

## Модель риска

Это объяснимая модель правил, а не обученный ML-прогноз. Она использует только текущий снимок: исходный кейс не содержит истории переходов статусов и удалений.

Каждая услуга оценивается отдельно по шкале 0–100. Вклад фактора равен `100 × значение фактора × вес / суммарный вес`; итог услуги — сумма вкладов (с ограничением 100). Значения факторов лежат в диапазоне 0–1:

| Признак | Начальный вес |
| --- | ---: |
| Дефицит средств на продления | 40 |
| Требуется ручное продление (автопродление выключено) | 45 |
| Срочность срока | 20 |
| Прогресс пятидневного `prolong_wait` | 5 |

Срочность линейно возрастает в течение семи дней перед продлением: `clip(1 − дней_до_срока / 7, 0, 1)`. Дефицит считается по общему кошельку аккаунта: доступный баланс расходуется по ближайшим срокам, одновременные продления делят покрытие пропорционально стоимости. Учитываются активные, приостановленные (они продолжают списывать оплату) и `prolong_wait` услуги. Для последнего статуса резервируется только текущая неоплата. Удалённые и заблокированные услуги исключаются. `not_performed` из снимка не считается признаком: в данных нет истории и контекста транзакций.

Индекс аккаунта — сумма оценок его услуг и может превышать 100. Пороги услуги и аккаунта настраиваются независимо (по умолчанию: средний от 30, высокий от 50). Для аккаунта с сотнями услуг это отражает масштаб совокупного риска. Услуги без даты или с противоречивой датой помечаются как неоценённые, остальные всё ещё оцениваются.

Денежные значения — сценарные индикаторы, не вероятность ухода, ожидаемая потеря или прогноз фактической выручки. Взвешенные продления считаются как `сумма стоимости запланированных продлений × score услуги / 100`; дополнительный индикатор показывает часть, не покрытую текущим доступным балансом. Расчёт предполагает текущий снимок и не моделирует будущие пополнения.

```text
индекс услуги = Σ(100 × значение фактора × вес / сумму весов)
индекс аккаунта = Σ индексов оценённых услуг
взвешенные продления = Σ(стоимость продлений услуги × индекс услуги / 100)
```

Доступный баланс — основной баланс плюс бонусный, если `bonusState` разрешает его тратить. Выводимый баланс не считается средствами для автопродления. Все поля `balance`, `price`, `amount` и `totalReplenished` принимаются в минимальных денежных единицах (евроценты); API хранит и возвращает их как поля `*_minor`.

Горизонт (30 дней), окно срочности (7 дней), период `prolong_wait` (5 дней), пороги услуги/аккаунта и веса редактируются через API. PATCH настроек сохраняет изменения в SQLite и рассылает SSE-событие активным клиентам.

## API

Все endpoints под `/api/v1`, кроме `/metrics` и `/healthz`. Данные клиентов, настройки, импорт снимка и метрики требуют действующую HTTP-only cookie-сессию. Для Prometheus можно задать отдельный `AEZA_METRICS_TOKEN` и отправлять его как Bearer token. Swagger и OpenAPI доступны в development; в production они выключены по умолчанию (`AEZA_DOCS_ENABLED=true` включает их явно).

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/auth/login` | Создать сессию по логину и паролю |
| `GET` | `/api/v1/auth/me` | Текущий пользователь |
| `POST` | `/api/v1/auth/logout` | Завершить сессию |
| `GET` | `/api/v1/customers` | Рейтинг, поиск, фильтр и сортировка |
| `GET` | `/api/v1/customers/{id}` | Услуги, транзакции, признаки и расчёт клиента |
| `GET` | `/api/v1/analytics/summary` | Сводные риски и сценарные суммы продлений |
| `GET` | `/api/v1/model/settings` | Действующие веса, пороги и описание признаков |
| `PATCH` | `/api/v1/model/settings` | Изменить часть настроек с автопересчётом |
| `PUT` | `/api/v1/source/snapshot` | Полностью заменить исходный снимок |
| `GET` | `/api/v1/events` | SSE для обновления панели без reload |
| `GET` | `/metrics` | Метрики Prometheus |
| `GET` | `/api/v1/docs` | Swagger UI |

Полная спецификация находится в [`backend/openapi.yaml`](backend/openapi.yaml). Входной формат снимка принимает поля кейса в `camelCase` (`balance`, `withdrawBalance`, `bonusBalance`, `bonusState`, `totalReplenished`, `autoprolong`, `paymentTerm`, `expiresAt`) и нормализованные поля `*_minor`.

Сортировка клиентов: `sort_by=id|email|balance|total_replenished|risk_score|potential_loss`, `order=asc|desc`. Пример: `/api/v1/customers?sort_by=balance&order=asc`.

## Данные и ограничения

При первом запуске создаётся небольшой синтетический снимок с адресами домена `.example`; он нужен только для демонстрации. Внешний набор тестовых данных сам не загружается. Передай снимок через `PUT /api/v1/source/snapshot`, когда он будет доступен в разрешённом формате.

Сессии хранят только SHA-256 хеши случайных токенов. Cookie имеет флаги `HttpOnly` и `SameSite=Lax`; в production обязателен `Secure`. Вход ограничен по частоте в Nginx и по адресу клиента в SQLite; сохраняется только keyed hash адреса. Изменяющие запросы проверяют `Origin` и Fetch Metadata, а снимок имеет ограничения на размер и число записей. SSE очереди ограничены и отбрасывают старые события, поскольку интерфейсу достаточно последнего состояния. API разрешает браузерные запросы только с origins, перечисленных в `AEZA_ALLOWED_ORIGINS`.

Docker Compose запускает API от непривилегированного пользователя с read-only root filesystem, без Linux capabilities и с `no-new-privileges`. Интерфейс отдаётся с CSP и защитными HTTP-заголовками; шрифт Onest хранится локально, внешние запросы к Google Fonts не нужны.
