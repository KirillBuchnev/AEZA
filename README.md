# AEZA — анализатор риска оттока

Аналитическая панель для маркетолога. Отвечает на три вопроса: кому из клиентов нужно внимание, почему возник риск и сколько денег бизнес может потерять. Отдельно показывает отток: сколько услуг сейчас под риском, сколько непродлений ожидается и что уже произошло по данным снимков.

Стек: FastAPI и PostgreSQL (бэкенд: SQLAlchemy и psycopg), React и Vite (панель, макет — Figma «AEZA — Пульс продлений»), nginx как обратный прокси, Docker Compose для запуска.

## Быстрый старт

Нужен Docker с Compose.

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- Панель: <http://localhost:5173>
- Swagger UI: <http://localhost:8001/api/v1/docs>
- OpenAPI JSON: <http://localhost:8001/api/v1/openapi.json> (та же спецификация лежит в `backend/openapi.json`)
- Проверка работоспособности: <http://localhost:8001/healthz>

Вход в панель для локального запуска:

```text
Логин: demo
Пароль: local-demo-change-this-password
Кодовое слово (для восстановления пароля): demo-codeword
```

Сразу после запуска в панели уже есть данные кейса (10 аккаунтов, 30 услуг, 100 транзакций) и 14 сценарных аккаунтов S01–S14 (см. «Данные»).

### Вход через SSO (необязательно)

В стенде есть локальный провайдер OpenID Connect (Dex). Он включается отдельным файлом Compose:

```bash
docker compose -f docker-compose.yml -f docker-compose.sso.yml up --build
```

На экране входа появится кнопка «Войти через SSO». Демо-учётная запись провайдера: `analyst@aeza.example` / `AezaSso-2026`. Она существует только в этом стенде. Вход по логину и паролю остаётся доступен.

### Без Docker

```bash
cd backend && pip install -r requirements-dev.txt
AEZA_DATABASE_URL=postgresql+psycopg://aeza:пароль@127.0.0.1:5432/aeza uvicorn app.main:app --port 8000

cd frontend && npm install
AEZA_API_TARGET=http://127.0.0.1:8000 npm run dev -- --host 127.0.0.1
```

Без `AEZA_DATABASE_URL` приложение открывает файл SQLite из `AEZA_DATABASE_PATH` (по умолчанию `data/aeza.db`): так проще проверить без сервера базы.

Панель открывается по `http://127.0.0.1:5173`. Этот адрес разрешён в `AEZA_ALLOWED_ORIGINS`.

### Тесты

```bash
cd backend
pip install -r requirements-dev.txt

```

161 тест: контрольные случаи модели, агрегация аккаунта, деньги (пара «ожидаемо / максимум» на одной выборке) и прогноз, журнал переходов и оценка удалений, сроки оплаты, устойчивость снимка к неизвестным значениям, сортировка, версия расчёта, настройки и перезапуск, данные кейса, выгрузки, метрики, соответствие спецификации, регистрация, сброс и смена пароля, ограничения частоты, OIDC с подставным провайдером и с внутренним адресом, сценарные аккаунты S01–S14, миграция из SQLite в PostgreSQL и разбор адреса базы.

Тесты идут на SQLite. Полный прогон на PostgreSQL, включая миграцию:

```bash
cd backend
AEZA_TEST_DATABASE_URL=postgresql+psycopg://пользователь:пароль@хост:5432/aeza_test pytest
```

Имя базы должно содержать `test`: фикстура очищает схему `public` перед каждым тестом.

## Данные

### Набор кейса

Файл `db/002_seed.sql` содержит тестовый набор кейса: 10 аккаунтов, 30 услуг, 100 транзакций. Из него сборка `backend/scripts/build_case_snapshot.py` создаёт снимок `backend/app/seeds/case_snapshot.json`. Тест проверяет, что закоммиченный снимок совпадает со сборкой.

Переменная `AEZA_SEED` выбирает данные для пустой базы:

- `case` (по умолчанию в коде) — набор кейса;
- `showcase` (так задан `.env.example`) — набор кейса без изменений плюс 14 сценарных аккаунтов S01–S14: их даты считаются от текущего времени и пересобираются при каждом старте;
- `demo` — синтетический набор с адресами `.example`;
- `empty` — база без клиентов, данные загружаются через API.

`AEZA_SEED` действует только на пустую базу. Чтобы заново загрузить набор, загрузите снимок через API или удалите том `aeza-pg` (`docker compose down -v` удалит все тома стенда).

На наборе кейса с настройками по умолчанию сейчас: 3 клиента с оценкой (два высоких, один средний), 7 без оценки. У трёх из них есть услуги с истёкшим сроком при статусе «активна» (4 такие услуги), у четырёх нет активных услуг. Шесть услуг в ожидании оплаты дольше пяти дней помечены как `grace_expired`: по правилам кейса их давно следовало перевести в `deleted`, поэтому их деньги в оценку не входят. Денежная оценка по набору на 24.10.2026: ожидаемо 2,45 € из максимума 5,47 € (одна услуга в среднем риске), нехватки средств нет, потому что балансы покрывают ближайшие продления. Это корректный результат, а не ошибка, и панель объясняет разницу.

Сценарии нужны потому, что балансы оригинала (35–915 €) минимум в 6 раз больше цены самой дорогой услуги аккаунта (0,72–9,60 €): нехватка средств всегда 0, а ситуации из ТЗ почти не встречаются. Подробный разбор и обоснование подачи результата — в `docs/notes/CHURN_RISK_RESEARCH.md`.

### Сценарий защиты

Слайд 12 презентации просит показать полный путь: найти клиента, объяснить причины и деньги, изменить коэффициент или данные, показать обновление.

1. **Найти.** Обзор: в высоком и среднем риске 9 клиентов из 24. Очередь идёт по ожидаемой потере: первым S06 (годовая услуга 720 € при низком риске даёт 121,68 € ожидаемо), вторым S03.
2. **Объяснить.** Карточка S03: «Не хватает средств» (36,4), «Срочность продления» (18,2), «Ожидание оплаты» (0,9), вместе 55,5; ожидаемо 33,30 € из максимума 60,00 €; действие — пополнить на 60,00 €.
3. **Изменить и показать обновление.** «Модель риска»: вес «Ручное продление» 45 → 20. S01 переходит из «Высокий» (52,1) в «Средний» (41,5) без перезагрузки страницы. Вернуть 45.

### Формат снимка (DTO между источником и анализатором)

Источник передаёт полный снимок: `PUT /api/v1/source/snapshot` с телом `{"customers": [...]}`. Поля — как в кейсе, суммы в евроцентах:

```json
{
  "customers": [
    {
      "id": "1",
      "email": "user-0001@example.test",
      "balance": 83810,
      "withdrawBalance": 14592,
      "bonusBalance": 4506,
      "bonusState": "locked",
      "totalReplenished": 96922,
      "services": [
        {
          "id": "1",
          "name": "service-0001",
          "price": 1500,
          "autoprolong": false,
          "paymentTerm": "month",
          "status": "active",
          "expiresAt": "2026-11-20T00:00:00.000Z"
        }
      ],
      "transactions": [
        {
          "id": "1",
          "serviceId": "1",
          "status": "not_performed",
          "type": "prolong",
          "amount": 1500,
          "createdAt": "2026-10-20T10:00:00.000Z"
        }
      ]
    }
  ]
}
```

Правила приёма:

- неизвестные поля игнорируются;
- неизвестный статус услуги или тип транзакции не отклоняет снимок: объект не участвует в расчёте и попадает в качество данных;
- дубликаты ID клиентов, услуг или транзакций отклоняют снимок целиком;
- лимиты: до 5 000 клиентов, по 5 000 услуг и 10 000 транзакций на клиента, не больше 50 000 услуг и транзакций всего.

Ответ содержит `snapshot_id`, число записанных фактов журнала, отчёт о качестве данных и сводку. Тот же файл можно загрузить на странице «Источник данных».

## Модель риска

Модель экспертная. Веса заданы командой и согласованы с ментором, а не обучены на исходах. Индекс показывает риск неоплаты продления, а не вероятность ухода клиента.

### Признаки и веса

| Признак | Вес | Когда срабатывает |
| --- | ---: | --- |
| Ручное продление `autoprolong_disabled` | 45 | автопродление выключено, срок продления в ближайшие 7 дней |
| Нехватка средств `insufficient_balance` | 40 | доступного баланса не хватает на продление этой услуги |
| Срочность `renewal_urgency` | 20 | есть ручное продление или нехватка средств, вклад растёт к сроку |
| Ожидание оплаты `prolong_wait` | 5 | услуга уже ждёт оплаты, вклад растёт за 5 дней grace-периода |

Выключенное автопродление и нехватка денег — главные признаки: в первом случае клиенту нужно продлить услугу самому, во втором списание не пройдёт. Близкий срок усиливает риск. Статус `prolong_wait` весит мало: без автопродления услуга всё равно требует ручной оплаты, а с автопродлением и деньгами списание пройдёт, и риск низкий.

### Формула

```text
urgency          = clip(1 − (due_at − now) / 7 дней, 0, 1)      # для prolong_wait = 1
manual_renewal   = urgency, если автопродление выключено
payment_distress = clip(недостаток_по_услуге / цена, 0, 1) × urgency
renewal_urgency  = urgency, если есть manual_renewal или payment_distress
grace_progress   = прошло_дней_ожидания / 5, только для prolong_wait

индекс услуги   = 100 × (45·manual_renewal + 40·payment_distress + 20·renewal_urgency + 5·grace_progress) / Σвесов
индекс аккаунта = 100 × (1 − Π (1 − индекс услуги / 100))      # хотя бы одна услуга не продлится
```

Нормализатор — сумма весов (по умолчанию 110), поэтому индекс услуги от 0 до 100 при любых весах из панели. Индекс округляется до одного знака после запятой.

Индекс аккаунта тоже лежит в 0–100, а у аккаунта с одной услугой равен индексу этой услуги. Две услуги с индексом 58 дают 82,4, а не 116: сумма росла бы вместе с числом услуг и выходила за шкалу. Простая сумма остаётся в ответе API как `account_risk_sum` для справки. Это индекс экспертной модели, а не откалиброванная вероятность.

Доступный баланс аккаунта общий для всех его услуг. Он распределяется по услугам в порядке оплаты: сначала ожидающие оплаты, затем по ближайшей дате продления.

### Контрольные случаи

Четыре аккаунта из обсуждения с ментором, у каждого одна услуга за 10 €:

| Ситуация | Индекс | Уровень | Ожидал ментор |
| --- | ---: | --- | --- |
| а. `prolong_wait` 1 день, баланс 0 | 55.5 | высокий | высокий |
| б. продление через 3 часа, автопродление выключено, денег хватает | 58.0 | высокий | высокий |
| в. продление через 3 часа, автопродление включено, баланс 0 | 53.6 | высокий | высокий |
| г. `prolong_wait` 1 день, автопродление включено, денег хватает | 0.9 | низкий | низкий |

Значения закреплены тестами. Панель пересчитывает их из текущих весов на странице модели, так что видно, как изменение коэффициента сдвигает случаи.

### Уровни

- Уровень услуги: средний от 30, высокий от 50.
- Уровень аккаунта считается по индексу аккаунта и имеет собственные пороги (по умолчанию тоже 30 и 50, допустимы 0–100): с числом рискованных услуг шанс, что хотя бы одна не продлится, растёт сам собой.
- Если у активной услуги нет даты окончания или дата уже прошла, у услуги нет индекса, а у аккаунта «Нет оценки» с задачей на исправление данных. Остальные услуги аккаунта рассчитываются и видны в карточке.
- Услуга в ожидании оплаты без даты окончания тоже не получает оценку: без даты нельзя измерить grace-период.

### Почему клиент в списке

Каждая причина приходит с вкладом в баллах и аргументом с цифрами, например:

- «На продление хватает 0,00 € из 100,00 €, не хватает 100,00 €. Без пополнения списание не пройдёт.»
- «Автопродление выключено, продление через 3 ч. Клиент должен продлить услугу сам, иначе она уйдёт в ожидание оплаты.»
- «Услуга ожидает оплаты 1,0 дн. после окончания срока; осталось 4 дн. grace-периода.»

Сумма вкладов равна индексу точно: баллы округляются до десятых так, чтобы слагаемые сошлись с итогом. У аккаунта вклады признаков по всем его услугам приводятся к индексу аккаунта пропорционально. Для каждой услуги и аккаунта есть рекомендуемое действие: пополнить баланс на конкретную сумму, напомнить о ручной оплате, проверить списание, исправить данные или запланировать пополнение, если срок вне недельного окна. Неуспешная оплата за последние 7 дней в индекс не входит, потому что по одному снимку нельзя отличить сбой от отказа, но попадает в рекомендацию.

### Деньги

```text
выборка                            = услуги с индексом больше 0, решение по которым впереди:
                                     срок в пределах 7 дней или ожидание оплаты меньше 5 дней
ожидаемо (revenue_at_risk)         = Σ цена услуги × индекс услуги / 100      по выборке
максимум (near_term_loss)          = Σ цена услуги                            по той же выборке
из ожидаемого: не хватает средств  = Σ недостаток на продление × индекс услуги / 100
                                     (potential_loss)
стоимость в месяц                  = Σ цена услуги / месяцев в сроке оплаты
```

Обе суммы считаются на одной выборке, поэтому всегда выполняется «не хватает средств ≤ ожидаемо ≤ максимум»: тест проверяет это на каждом сценарном аккаунте. Очередь клиентов по умолчанию идёт по ожидаемой потере (`sort_by=revenue_at_risk`, по убыванию), равные суммы упорядочены по индексу аккаунта; клиенты без оценки в конце.

Срок `hour` переводится в 1/720 месяца, `week` — в 7/30 месяца, `quarter_year` — в 3 месяца. Нехватка средств равна нулю, когда балансы покрывают продления: тогда деньги не нужны, и клиент продлит сам. «Ожидаемо» показывает стоимость того, что может не продлиться, даже если деньги есть, например при ручном продлении.

Ручное продление через три часа при достаточном балансе даёт индекс 58: ожидаемо — 58 % цены, максимум — вся цена. Максимум не оценка вероятности, а верхняя граница: он равен полной цене даже у услуги с индексом 0,9 (S04), поэтому для решений опирайтесь на «ожидаемо». Услуга, которая ждёт оплаты дольше 5 дней, в выборку не входит: по правилам кейса она уже должна быть удалена, это проблема данных (`grace_expired`). Окно в 7 дней задаёт `ACTION_HORIZON_DAYS` в `backend/app/risk.py`.

### Отток: факты и прогноз

- **Факты** — переходы статусов между снимками из журнала: продлено, ушло в ожидание, удалено, заблокировано, пропало из источника. Первая загрузка журнал только открывает. Пока переходов нет, факты оцениваются по статусам текущего снимка: удалённую услугу относим к дате окончания срока. Такие значения помечены «(оценка)».
- **Прогноз** — услуги, чьё решение наступает в горизонте. Столбики показывают, сколько из них под риском (высокий или средний уровень), точки — ожидаемое число непродлений: сумма индексов, делённая на 100. Услуга в ожидании оплаты ставится на день, когда по правилам кейса она станет `deleted` (окончание срока плюс 5 дней). Услуги, просроченные сверх пяти дней, на график не попадают: по правилам они уже должны быть удалены, их число показано отдельно как проблема данных. Это оценка по индексу, она не откалибрована по историческим исходам.
- На графике факты сплошные слева от линии «сегодня», услуги под риском штрихованные справа. Плашки над графиком: сколько ушло, сколько под риском в горизонте, сколько ждут оплаты. Ось целая: число услуг не бывает дробным.

### Почему без машинного обучения

Для обучения нужны размеченные исходы: какие услуги продлились, а какие нет. В снимке кейса их нет, есть только текущее состояние. Модель, обученная без исходов, подгонялась бы под предположения. Экспертный индекс прозрачен, его можно проверить вручную и настроить в панели.

Путь к ML заложен: журнал переходов накапливает метки `prolong_wait → active` (продлено) и `→ deleted` (не продлено). Когда исходов станет достаточно, сначала откалибруются веса текущей формулы, и только потом сравнивается обученная модель на тех же признаках — по качеству и по стабильности объяснений.

### Как добавить признак

1. В `backend/app/risk.py` добавить вес в `DEFAULT_WEIGHTS`, описание в `FACTORS`, вклад в `contributions` внутри `_evaluate_service` и текст аргумента в `_explain`.
2. Ключи весов в `PATCH /api/v1/model/settings` берутся из `DEFAULT_WEIGHTS`; нормализатор пересчитывается сам.
3. Панель получает список признаков из `GET /api/v1/model/settings` и показывает его на странице модели без правки фронтенда.
4. Добавить контрольный случай в `backend/tests/test_model_contract.py`.

Каждое изменение весов увеличивает ревизию. Ответы содержат `calculation_version` (версия модели и ревизия) и `snapshot_id`, поэтому видно, по каким данным и весам получена оценка.

## Архитектура

```text
браузер ──► nginx (frontend, 10.233.40.10) ──► FastAPI (api) ──► PostgreSQL (том aeza-pg)
               │  статика React                  │  расчёт риска по запросу
               │  /api, /metrics → api           │  SSE /api/v1/events
               │  /dex → провайдер SSO (опция)   │  /metrics для Prometheus
               └  лимиты частоты на вход и сброс └  выгрузки CSV, XLSX, XML
```

- `backend/app/risk.py` — модель: признаки, индекс услуги и аккаунта, причины, рекомендуемые действия, качество данных, прогноз. Чистые функции без доступа к базе.
- `backend/app/database.py` — снимок, журнал переходов, настройки модели, пользователи, сессии, ограничения частоты.
- `backend/app/main.py` — HTTP-контракт, сессии, сортировка и фильтры, SSE, метрики, выгрузки.
- `backend/app/oidc.py` — вход через OpenID Connect: authorization code с PKCE, проверка `id_token` по ключам провайдера.
- `backend/app/seeds.py`, `backend/app/seeds/case_snapshot.json` — данные для пустой базы.
- `backend/app/exports.py` — выгрузки CSV, XLSX и XML с защитой от формул в ячейках.
- `frontend/src` — экраны: вход, обзор, клиенты, карточка клиента, модель риска, источник данных.
- `backend/openapi.json` — спецификация, генерируется из приложения скриптом `backend/scripts/export_openapi.py`.

Оценки считаются при каждом запросе по текущему снимку, текущим весам и текущему времени. Поэтому срочность растёт сама по мере приближения срока, а изменение данных или коэффициентов сразу видно в панели.

Выгрузки не содержат служебных таблиц: сессий, пользователей, попыток входа, хешей и настроек. В CSV и XLSX текст, который Excel может принять за формулу, сохраняется как текст.

## Аутентификация

- **Регистрация** — фамилия, имя, отчество (необязательно), логин, пароль и кодовое слово. Включена в разработке, выключена в production по умолчанию: `AEZA_REGISTRATION_ENABLED`.
- **Забыли пароль** — логин и кодовое слово (регистр не важен), затем новый пароль. Токен сброса действует 10 минут и срабатывает один раз. После сброса сессии пользователя закрываются.
- **Смена пароля** — из боковой панели, с проверкой текущего пароля.
- **Правила** — пароль от 10 до 128 символов, буквы и цифры, не совпадает с логином. Кодовое слово от 6 до 64 символов, не только цифры и не типовое слово. Логин от 3 до 64 символов: латиница, цифры, `. _ @ -`. Пароль и кодовое слово хранятся как scrypt-хеши.
- **Защита от перебора** — за 15 минут: 5 неверных входов с одного адреса и 10 на один логин; 30 проверок кодового слова с адреса и 5 на логин; 5 попыток смены пароля. Адрес клиента берётся из `X-Real-IP` только от прокси из `AEZA_TRUSTED_PROXY_IPS`. Локально Docker подменяет адрес на шлюз сети, поэтому все браузеры одной машины делят лимиты.
- **Первый администратор** создаётся из `AEZA_ADMIN_*`, только если такого логина ещё нет.

### SSO (OpenID Connect)

Переменные (в стенде заданы через `docker-compose.sso.yml`):

```text
AEZA_OIDC_ISSUER=https://sso.example.com/realms/aeza   # публичный адрес провайдера (в iss и в переходах браузера)
AEZA_OIDC_INTERNAL_ISSUER=                              # адрес для серверных запросов, если он другой (например, в сети контейнеров)
AEZA_OIDC_CLIENT_ID=aeza-panel
AEZA_OIDC_CLIENT_SECRET=...
AEZA_OIDC_REDIRECT_URI=https://panel.example.com/api/v1/auth/oidc/callback
AEZA_OIDC_SCOPES=openid profile email
AEZA_OIDC_AUTO_PROVISION=false                          # true — создавать пользователя при первом входе
AEZA_OIDC_USERNAME_CLAIM=preferred_username
```

Поток: authorization code с PKCE (S256); `state` и `nonce` одноразовые и живут 10 минут. `id_token` проверяется по ключам JWKS провайдера: подпись (только асимметричные алгоритмы), `iss`, `aud`, `exp`, `nonce`. Учётная запись SSO связывается с локальной по паре issuer и subject. Автоматически связать SSO с существующим локальным логином нельзя, иначе чужая учётная запись провайдера получила бы доступ к чужому аккаунту. У SSO-пользователя нет локального пароля: вход по паролю для него не работает. Провайдер, отданный через `/dex`, — только для локального стенда.

Новый снимок загружается через `PUT /api/v1/source/snapshot` или со страницы «Источник данных». Загрузка заменяет клиентов, услуги и транзакции целиком, журнал переходов дополняется, настройки модели и пользователи не меняются.

### Переход с SQLite на PostgreSQL

Стенды, которые работали на SQLite, хранили данные в томе `aeza-data`. Один раз после запуска стека скопируйте их в PostgreSQL:

```bash
docker compose exec -T api python -m app.migration /data/aeza.db
```

Снимок заменяется данными файла; учётные записи, сессии и попытки входа объединяются по ключу, поэтому повторный запуск безопасен. Файл открывается только для чтения: том `aeza-data` монтируется в API как `ro`.

### Безопасность

Сессии хранят только SHA-256 хеши случайных токенов. Cookie `HttpOnly` и `SameSite=Lax`. Изменяющие запросы проверяют `Origin` и Fetch Metadata. SSE-очереди ограничены и отбрасывают старые события. Compose запускает API и панель с read-only файловой системой, без Linux capabilities и с `no-new-privileges`. Панель отдаётся с CSP и защитными заголовками, шрифты хранятся локально.

Swagger открыт без входа, потому что это описание API без данных. В production он выключен по умолчанию.

## Решения и ограничения

- **Хранилище — PostgreSQL.** Схема создаётся при запуске командами `CREATE ... IF NOT EXISTS` под общей блокировкой, поэтому повторный старт безопасен; миграции Alembic пока не нужны. В схеме нет ограничений `CHECK` на статусы и даты снимка: неизвестные значения принимаются и видны в «Качестве данных». Драйвер — psycopg 3. События SSE рассылаются внутри одного процесса API, поэтому несколько реплик API потребуют `LISTEN/NOTIFY`. Ранний черновик `docs/postgres-prototype/` и `db/004_backend.sql` — ориентир по типам; рабочий путь описан здесь.
- **Прогноз и денежная оценка — ориентиры.** Они не откалиброваны по историческим исходам, а команда задала их как экспертные оценки.
- **Удаления до появления журнала — оценка.** В снимке нет даты удаления, поэтому её заменяет дата окончания срока, и факт помечен как оценка.
- **Лимиты входа в Docker** общие для всех браузеров одной машины, потому что видно только адрес шлюза.
- **SSO-провайдер в стенде — учебный.** Учётная запись `analyst@aeza.example` существует только в `sso/dex/config.yaml`; для продакшена нужен свой провайдер.
- **Выгрузка и API не отдают секреты:** хеши, токены и служебные таблицы исключены из выгрузок.
